1Guide de déploiement

Toute l'infrastructure est décrite en Terraform (modules network, ecr, rds, alb, ecs). Le déploiement se fait avec vos propres identifiants AWS : grâce à l'auto-détection du compte, aucun fichier de configuration n'est nécessaire — Terraform déduit le LabRole du compte et génère automatiquement la clé JWT.

Prérequis. aws CLI, terraform (≥ 1.5) et docker installés. Les commandes ci-dessous se lancent depuis le dépôt cloné. La durée totale est d'environ 15–20 minutes (la création de RDS Multi-AZ domine ce temps).

  1. Renseigner vos identifiants AWS Dans le lab AWS Academy : AWS Details → AWS CLI, puis copier le bloc [default] dans ~/.aws/credentials (identifiants temporaires, à rafraîchir à chaque session). Fixer ensuite la région et vérifier : 
    aws configure set region us-west-2
aws sts get-caller-identity     # doit afficher votre compte → OK
  2. Créer les dépôts d'images ECR Les tâches ECS ne peuvent pas démarrer avant que les images existent : on crée donc ECR en premier. 
    cd infra
terraform init
terraform apply -target=module.ecr
  3. Construire et pousser les images Docker Build en linux/amd64 obligatoire (Fargate est x86_64), depuis le dossier infra avec la racine du dépôt comme contexte (..). 
    ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
ECR=$ACCOUNT.dkr.ecr.us-west-2.amazonaws.com
aws ecr get-login-password --region us-west-2 | docker login --username AWS --password-stdin $ECR
docker build --platform linux/amd64 -f ../backend/Dockerfile  -t $ECR/conduit-backend:latest  ..
docker build --platform linux/amd64 -f ../frontend/Dockerfile -t $ECR/conduit-frontend:latest ..
docker push $ECR/conduit-backend:latest
docker push $ECR/conduit-frontend:latest
  4. Déployer toute l'infrastructure VPC, RDS Multi-AZ (~10–15 min), ALB et services ECS, en une commande. 
    terraform apply
  5. Vérifier le déploiement L'URL publique de l'ALB est exposée en sortie Terraform. La SPA doit répondre 200 et l'API renvoyer du JSON. 
    URL="http://$(terraform output -raw alb_dns_name)"
curl -I "$URL/"            # SPA React      → 200
curl    "$URL/api/tags"    # backend + RDS  → JSON
  6. Détruire après la démonstration Pour éviter toute consommation. Terraform détruit dans l'ordre inverse des dépendances ; conserver terraform.tfstate jusqu'à la fin. 
    terraform destroy

Si un jeton expire pendant un apply. Le compte académique impose des identifiants STS temporaires. En cas d'expiration, rafraîchissez les identifiants (étape 1) et relancez terraform apply : la commande est idempotente et reprend où elle s'était arrêtée.

2Contexte et objectifs

Conduit est une application full-stack de référence (clone de Medium) implémentant la spec RealWorld. C'est un monorepo composé de deux services déjà conteneurisés :

  • backend — API REST Express 5 + PostgreSQL via Sequelize 6, endpoints authentifiés par JWT sous /api.
  • frontend — SPA React 18 (Vite) servie par nginx ; tous les appels API utilisent des chemins relatifs /api/….

Les identifiants de base de données et la clé JWT sont pilotés par variables d'environnement (config/config.js).

Exigence de l'énoncé. Créer au minimum un VPC avec plusieurs subnets répartis sur plusieurs zones de disponibilité. L'architecture applicative est libre ; l'objectif est une infrastructure logique, robuste, résiliente et scalable, en expliquant les choix, les composants et les flux (least privilege).

3Choix de l'architecture

Critère central : maximiser résilience et scalabilité sans réécrire l'application, qui est déjà conteneurisée.

OptionDécisionJustification
ECS Fargate + ALB + RDS Retenu Les conteneurs tournent tels quels, sans réarchitecture. Fargate supprime toute gestion d'OS (pas d'AMI à patcher). Multi-AZ et auto-scaling natifs. Meilleur ratio effort/résilience.
EC2 Auto Scaling Group + ALB Écarté Introduit la gestion d'AMI/OS et des launch templates sans bénéfice à cette échelle : gérer des serveurs pour exécuter des conteneurs est inférieur à Fargate ici.
Full serverless (Lambda + API Gateway) Écarté Express 5 + sequelize.sync() et le pooling ne sont pas serverless-native. L'adaptation (cold starts, stratégie de connexion) serait une réécriture non justifiée.

ECS Fargate s'impose : l'infrastructure ajoute le placement multi-AZ, l'auto-scaling et un plan de contrôle managé, sans surcoût d'administration système.

4Schéma d'architecture

Le schéma interactif ci-dessous (Excalidraw) présente le VPC à trois tiers, le flux des requêtes et le placement multi-AZ. On peut zoomer et se déplacer à l'intérieur du cadre.

VPC 10.0.0.0/16 (us-west-2) — Internet → ALB (tier public) → ECS Fargate frontend/backend (tier privé app) → RDS PostgreSQL Multi-AZ (tier privé data).

Trois principes structurent ce schéma : (1) l'ALB est le seul composant exposé sur Internet ; (2) les tâches applicatives vivent dans des subnets privés sans route Internet (les accès aux services AWS passent par des VPC Endpoints, sans NAT) ; (3) la base est isolée dans un troisième tier, joignable uniquement depuis l'app.

5Réseau et composants applicatifs

Découpe du VPC (trois tiers, deux AZ)

TierAZCIDRContenu
Public2a / 2b10.0.0.0/24 · 10.0.1.0/24Application Load Balancer
Privé app2a / 2b10.0.10.0/24 · 10.0.11.0/24Tâches ECS Fargate
Privé data2a / 2b10.0.20.0/24 · 10.0.21.0/24RDS PostgreSQL (primaire/standby)

Les subnets publics routent 0.0.0.0/0 → Internet Gateway. Les subnets privés n'ont pas de route par défaut (pas de NAT Gateway).

Pourquoi pas de NAT ? Conduit n'émet aucun appel sortant Internet à l'exécution : il ne parle qu'à RDS (réseau privé) et tire son image via VPC Endpoint. Supprimer la NAT économise ~32 $/mois/AZ et réduit la surface d'attaque (une tâche compromise ne peut ni exfiltrer ni télécharger). Tous les accès AWS passent par des VPC Endpoints internes (ECR, S3, CloudWatch Logs, Secrets Manager).

ALB, ECS et RDS

  • ALB — seul point d'entrée Internet, déployé sur les deux subnets publics. Routage par chemin : /api/* → backend Express :3001 (health GET /api/tags), /* → nginx :80 (health GET /). Le frontend ne fait aucun proxy : c'est l'ALB qui sépare /api/*.
  • ECS Fargate — cluster conduit-cluster, deux services dans les subnets privés app, sans IP publique, répartis sur les deux AZ. conduit-frontend (nginx, 2 réplicas) et conduit-backend (Express, 2 → 4 réplicas, auto-scaling CPU cible 60 %), chacun 0,25 vCPU / 512 Mo.
  • RDS PostgreSQL 16 — db.t4g.micro, 20 Gio gp3 chiffré, Multi-AZ (standby synchrone, bascule < 2 min), publicly_accessible = false. Identifiants générés et stockés dans Secrets Manager.

6Sécurité et moindre privilège

Chaîne de groupes de sécurité

Chaque tier n'accepte que le trafic du tier immédiatement en amont — par référence de groupe de sécurité, jamais par plage d'IP :

Internet ──:80/443──▶ ALB-SG    (entrant 80/443 depuis 0.0.0.0/0)
                          │
                          ▼
                       tasks-SG  (entrant 80 et 3001 UNIQUEMENT depuis ALB-SG)
                          ├──▶ rds-SG    (entrant 5432 UNIQUEMENT depuis tasks-SG)
                          └──▶ vpce-SG   (entrant 443  UNIQUEMENT depuis tasks-SG)

Seul l'ALB accepte une entrée large (80/443). Une tâche compromise est injoignable depuis Internet et n'atteint la base que par le port 5432 documenté. La connexion RDS est chiffrée en TLS (PostgreSQL 16 impose rds.force_ssl).

Rôles IAM

Le modèle nominal sépare le rôle d'exécution ECS (tirer l'image, injecter les secrets, streamer les logs — restreint au seul secret conduit/app) du rôle de tâche (assumé par l'application, aucune permission AWS car Conduit ne parle qu'à RDS via le réseau).

Contrainte du lab (LabRole). Le compte AWS Academy interdit iam:CreateRole : Terraform ne peut pas créer les deux rôles dédiés et bascule sur le rôle pré-existant LabRole (exécution + tâche). C'est un affaiblissement du moindre privilège au niveau IAM imposé par le lab ; dans un compte normal la séparation s'applique sans changer le code. Le moindre privilège réseau (chaîne de SG, isolation des subnets, absence de NAT) reste totalement intact.

7Résilience, scalabilité, observabilité

  • Multi-AZ — ALB réparti sur deux AZ ; 2 réplicas par service répartis sur les deux AZ (la perte d'une AZ laisse une tâche par service) ; RDS standby synchrone à bascule automatique.
  • Auto-scaling — target tracking sur le CPU moyen du backend à 60 % : de 2 à 4 tâches selon la charge.
  • Health checks & rolling deploys — l'ALB sonde chaque cible toutes les 30 s, retire une cible après 3 échecs ; ECS la remplace. Le drainage de 30 s assure des déploiements sans coupure.
  • Observabilité — CloudWatch Logs (un groupe par service, rétention 7 j) et Container Insights (CPU/mémoire/réseau par tâche). Les logs ont permis de diagnostiquer les incidents de déploiement.

Conséquence : le déploiement est manuel (pas de CI/CD fédéré), car le compte interdit les permissions IAM requises par l'OIDC. C'est un choix de périmètre assumé, non une fonctionnalité manquante.

Problèmes rencontrés et résolus

Trois incidents, tous diagnostiqués via CloudWatch Logs puis corrigés — le réseau a fonctionné dès le départ, seules des configurations applicatives ont été ajustées :

SymptômeCauseCorrectif
/api/tags → 500 (no encryption) PostgreSQL 16 impose TLS ; Sequelize se connectait en clair (le réseau, lui, joignait déjà RDS). SSL côté client via PROD_DB_SSL=true dans la task definition.
Service frontend : 0 tâche (CannotPullContainer) Image frontend pas encore poussée (token STS expiré) à la création du service. Push de l'image puis ecs update-service --force-new-deployment.
Tâches frontend en boucle de redémarrage nginx résolvait proxy_pass http://backend:3001 (nom docker-compose) au démarrage → introuvable dans Fargate. Suppression du bloc location /api/ : derrière l'ALB, nginx ne sert que la SPA.

Extensions futures

  • HTTPS — le SG de l'ALB pré-admet déjà 443 : attacher un certificat ACM et rediriger 80 → 443.
  • Troisième AZ — le code (count/for_each) supporte l'ajout d'une AZ.
  • État Terraform distant — backend S3 + verrou DynamoDB pour le travail collaboratif.
  • Endpoint /health dédié — découpler le health check du backend de la base.

Conclusion. L'application est pleinement opérationnelle sur l'infrastructure cible : frontend servi, API fonctionnelle, PostgreSQL accessible en TLS et persistante, le tout réparti sur deux AZ avec auto-scaling et isolation réseau à trois tiers.
